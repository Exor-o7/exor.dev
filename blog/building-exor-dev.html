Building Exor.dev

Site Build Log • UX • Iteration

Exor.dev started as a single static page and is gradually being expanded into a clearer multi-page portfolio. The goal is to keep it simple, fast, and easy to update while still making the site feel intentional.

A portfolio I can maintain

Exor.dev documents systems work, automation projects, and the technical direction I am developing alongside my IT career. It needs to make that work easy to find and be simple enough that adding a project or correcting a description is a small task.

The site uses HTML, CSS, and a small JavaScript file. GitHub Pages serves the files on a custom domain. There is no application server, package installation, or framework build step required to preview the site. That keeps the deployment model close to the content being published.

Separate identity from navigation

The homepage pairs the supplied ronin illustration with an introduction, featured projects, skills, experience, and writing. The illustration establishes the identity, while the links give a visitor a direct path to the work behind it.

Inner pages share the wordmark, cyan accents, calligraphy, and navigation, with layouts adapted to their content. The project directory uses filterable cards. The resume uses an experience timeline. Articles use a reading column and a section guide. The earlier terminal theme remains archived in the repository rather than being mixed into the current navigation.

Make JavaScript an enhancement

The projects exist as HTML articles before JavaScript runs. Search and category controls begin hidden and become available when their event handlers are attached. If scripts are disabled, a visitor still gets the complete directory and ordinary links.

The homepage has three static featured cards as a fallback. When served normally, JavaScript reads the project directory and refreshes the selection. It also updates the project count from the same directory. That reduces one source of duplicated content without making the first useful render depend on a request.

The tradeoff is that navigation markup is still repeated across static pages. Root pages and pages in subdirectories need different relative paths. Keeping that markup consistent is an explicit maintenance task, and local link checks help catch mistakes.

Check the things that can break quietly

The repository includes a local preview that omits production analytics and can disable scripts with a query parameter. That makes the fallback content easy to inspect separately from the interactive version.

python scripts/preview.py
# Open http://127.0.0.1:8765/
# Add ?nojs=1 to check the fallback.

python scripts/check_site.py
node --check js/index.js
git diff --check

The structural checker follows local links and fragment targets, checks duplicate IDs and image attributes, and verifies the project count and lifecycle order. It catches a missing page or stale anchor before deployment. JavaScript syntax validation catches a different class of error.

Neither replaces a browser check. A valid link can be difficult to tap, and valid CSS can still produce a cramped layout. The visual pass covers desktop and narrow screens, the mobile menu, keyboard focus, project filtering, and the empty state.

Let the content earn the design

The next step is depth: show how a project works, explain a decision, and link to evidence. The Janitorfin case study follows that approach with its actual workflow and source references. A downloadable resume gives visitors a portable account of the experience behind the projects.

The same rule applies to future changes to the site. Add a component when it helps someone understand the work or navigate it. Keep the content readable and the maintenance cost small enough that the portfolio can continue to reflect current work.
