Homelab Notes: What I Actually Learn

Homelab • Reliability • Operations

A homelab is useful because it teaches more than how to deploy services. It teaches troubleshooting, planning, tradeoffs, backup thinking, and the habit of improving systems after they break.

Start with the dependencies

My lab includes Proxmox, TrueNAS, Docker Compose, UniFi networking, Caddy, and a collection of media services. Listing those names explains what is installed. Understanding what must work before something else can work is more useful when a service fails.

Jellyfin needs access to its configuration and media. A reverse proxy needs a reachable upstream before it can serve that application. An automation that talks to Jellyfin, Radarr, or Sonarr also needs those APIs to be available. A visible failure at the edge may begin with a storage mount, a name-resolution problem, or an upstream application.

The stack overview groups the main areas of practice. For troubleshooting, I use a more specific question: which dependency would explain this symptom, and what evidence would distinguish it from the next possibility?

Collect evidence before changing state

For a Compose-managed service, a short initial sequence is configuration validation, container status, and a bounded slice of recent logs. Run these commands from the directory containing the relevant Compose file. They inspect the deployment; they do not restart or recreate its services.

docker compose config --quiet
docker compose ps
docker compose logs --tail 100 --timestamps

config --quiet checks the resolved configuration without printing it. A valid configuration does not prove that a mounted path exists, that a service can authenticate to an API, or that an application is healthy. Status and logs provide the next pieces of evidence.

Keep the log window bounded so a recent error is not buried in hours of output. Look for the first meaningful failure and its timing: a refused connection, an unavailable path, or an authentication error points to different next steps. Docker documents the configuration command and log options.

Running is not the same as ready

A container can be running while the application inside it is still starting. If another service begins work during that interval, a connection failure may look like a bad configuration even though the real issue is readiness.

Compose can use depends_on to establish startup order. Waiting for a dependency's health check requires the service_healthy condition; ordinary startup ordering alone does not establish application readiness. This behavior is described in Docker's startup-order documentation.

Health checks also have a scope. A successful HTTP response may tell me the application is listening without proving that it can read the media share or complete an integration request. The check should match the task the next service actually needs to perform.

Write a recovery plan that names the state

A recovery plan needs more than an image name. For each service, identify its persistent configuration, databases, media or user data, volume mappings, and required credentials. Those pieces can have different backup and recovery requirements.

  • Configuration: the Compose definition, environment settings, mounts, and application-specific configuration.
  • Application state: databases, accounts, scheduled work, and queues that determine what happens after a restart.
  • Content: the underlying datasets or shares used by the service.
  • Dependencies: storage availability, networking, DNS, and APIs the service needs to operate.

Janitorfin is a useful example of why this matters. Its pending-deletion queue contains saved deadlines. Restoring only the plugin binary does not restore that operational state. The queue and its meaning belong in the recovery plan.

Define what a successful restore means

The following is a recovery exercise outline, not a claim that every service in my lab has passed a measured recovery test. The first step is to choose a small, representative service and document what a successful recovery would look like.

  1. Identify a backup and the version of the application it belongs to.
  2. Restore the required state into an isolated test environment.
  3. Prevent scheduled jobs, notifications, and external write operations from acting on the live environment.
  4. Check that the application starts, its expected data is present, and a representative read operation succeeds.
  5. Record missing dependencies, manual steps, and elapsed recovery time for the next revision of the runbook.

A successful restore is stronger evidence than a successful backup job. It tests whether the saved data, application version, and recovery instructions are sufficient together.

What the lab teaches beyond self-hosting

The technical stack creates recurring opportunities to practice diagnosis: separate symptoms from causes, inspect before restarting, and verify the user-facing operation after a change. It also makes maintenance work visible. Updates, retention policies, saved state, and recovery instructions all become part of operating a service.

That is the connection to systems work. A useful lab develops the habit of asking what a system depends on, how its state changes, and how someone could recover it without relying on memory.
